# 方案：面部捕捉 + 功能扩展

> 目标：把「黑叶萤桌宠」从**只能自己动**的桌宠，扩成**能被你驱动**的桌宠；并评估把它做成一个「类 VTube Studio 的面捕软件」需要补什么。
>
> 本文是可行性评估与路线建议，不含实现。所有结论都标注了依据来源（代码行号 / 实测 / 官方文档）。

---

## 零、先说结论

三句话：

1. **模型不是瓶颈。** Hotaru2024 有 251 个参数，面捕需要的那一套（头部角度、眼开合、眼球、眉毛、嘴型、鼓腮、吐舌、脸红）**全都有**，覆盖率约 46/51。可以说这套参数就是照着面捕标准做的。
2. **真正的阻塞项是硬件：本机没有摄像头。** 全盘枚举 PnP 设备，没有 `usbvideo` 服务、没有 Camera 类设备，只有几个虚拟摄像头/虚拟显示器。这件事不定下来，后面都是空谈。
3. **动手写面捕之前，建议先补一层「参数仲裁」。** 现在 6 个模块都在抢同一批参数，靠 `app.ticker` 里的调用顺序和两个 `_holdUntil` 时间窗维持不打架——这套机制已经接近极限，再加第 7 个写者（面捕）会直接失控。这是**前置重构**，不是可选项。

## 二、本机环境的关键发现（三件事，按重要性排序）

### 2.1 没有物理摄像头（阻塞项）

实测枚举结果：

- `Get-PnpDevice -Class Camera,Image` → **无对象**
- `Win32_PnPEntity` 中 `Service = 'usbvideo'` → **无**
- 名称含 camera/webcam/摄像 的设备 → 只有 `nizima LIVE Virtual Camera`（`Service=VCamSDK`，**虚拟**摄像头驱动）
- 另有 `Lebo Virtual USB Monitor`、`seewo - Virtual MonitorX`、`Parsec Virtual USB Adapter` —— 都是虚拟显示器（这也解释了为什么 `screenTrack.screenIndex` 是 2）

**结论**：这台机器当前拿不到任何真实的摄像头画面。三条出路：

| 路线 | 成本 | 画质/精度 | 说明 |
|---|---|---|---|
| A. 买个 USB 摄像头 | ¥50–150 | 中 | 最直接。1080p30 即可，MediaPipe 只吃 640×480 |
| B. 用手机当摄像头 | ¥0 | 中 | Android 装 DroidCam/Iriun 提供**原始画面**给 PC，可直接复用路线 A 的全部代码 |
| C. 手机 ARKit 面捕 | ¥0（需 iPhone） | **最高** | 不传画面、只传 52 个 blendshape。VTube Studio 的招牌做法 |

⚠️ 注意区分：`nizima LIVE Virtual Camera` 输出的是**已渲染的角色画面**，不是摄像头原画，**无法**用来二次提取人脸。虚拟摄像头只有在「输出原始画面」时才有用。

### 2.2 你已经在这个生态里了（利好）

扫出来的痕迹：

- `D:\SteamLibrary\steamapps\common\VTube Studio` —— **VTS 本体已装**（Steam 版）
- 同目录 `Live2DModels\` 下有 **38 个模型**（Hotaru2024 / nyata / saki / KurobaHotaru / Memento …），也就是 `modelServeBase` 指向的那个库
- `E:\Live2D Cubism 5.3` —— **Cubism Editor 已装**（能自己改模型、做动作、调参数）
- `%APPDATA%\warudo-client-electron` + `warudo-mediapipe-electron` —— **Warudo 跑过**，它那个 `-mediapipe-` 组件正是 MediaPipe 面捕宿主，说明**这台机器上 MediaPipe 面捕跑通过**

**意义**：① 设备与算力已被验证能吃下 MediaPipe 面捕；② 你有 Cubism Editor，模型侧的改造（补动作、调参、加参数）不用求人；③ 参照物（VTS）就在本地，可以随时对照行为。

### 2.3 模型参数：面捕所需一应俱全（关键利好）

解密 `hotaru2024.cdi3.json.enc`（密钥在 `main.js:851`，`scryptSync('HotaruDesktopPet-Live2D-2024','static-salt-v1',32)`）后实测：

```
cdi3 Version 3 —— 参数 251 个 / 参数组 20 个 / 部件 32 个
moc3 明文 56.5 MB（这是内存占用 2.3 GB 的主因）
```

面捕直接要用到的参数，**全部存在**：

```
头部姿态   ParamAngleX / Y / Z              ParamBodyAngleX / Y / Z
眼开合     ParamEyeLOpen / ParamEyeROpen
眼球       ParamEyeBallX / ParamEyeBallY
挤眼       ParamEyeSquintL / ParamEyeSquintR
眉         ParamBrowLY / RY / ParamBrowLForm / RForm
嘴         ParamMouthOpenY / ParamMouthForm / ParamMouthX
下颌       ParamJawOpen / ParamJawOpen2
嘴形细节   ParamMouthFunnel / ParamMouthPuckerWiden / ParamMouthShrug
           ParamMouthPressLipOpen / ParamSilence
脸颊       ParamCheekPuff            舌   ParamTongueOut
元音       ParamA / I / U / E / O
脸红       Param194 / Param195       呼吸 ParamBreath
```

**两个需要留意的地方**：

1. **`Groups` 里 `LipSync` 的 `Ids` 是空数组**（`{"Name":"LipSync","Ids":[]}`）。所以框架的自动口型同步对这套模型无效——这解释了项目里为什么要自己写 viseme 引擎。面捕的口型也必须自己映射，不能指望框架。
2. **存在第二套角度参数**：`ParamAngleX2/Y2/Z2`、`ParamBodyAngleX2/Y2/Z2/Z3`（归属 `ParamGroup`，而现用的一套归属 `ParamGroup20`）。模型作者可能做了两段式头部。**要实测哪一套真正驱动头部**——如果 `X2` 才是生效的，现有代码就是在写一个死参数。

### 2.4 现有参数写入：没有仲裁层（必须先处理）

`app/js/live2d-loader.js:310` 的每帧循环：

```js
this.app.ticker.add(() => {
  ...
  if (this.idle && now >= this._motionHoldUntil) this._idle(t, dt);  // 头部角度基线、呼吸、视线、额外参数
  this._mouth(dt);        // ParamMouthOpenY / 元音
  this._blinkUpdate(dt);  // ParamEyeLOpen / ROpen
  this._express(dt);      // 五官（眼、眉、嘴角、鼓腮、吐舌、脸红）—— 注释要求"必须在眨眼之后，乘算眼开合"
  this._musicTick(dt);    // ParamAngleY 点头 + 压低眼睛 —— 注释要求"覆盖在表情层之后，确保闭眼生效"
});
```

也就是说，**不打架靠的是两条隐性契约**：

- 调用顺序（注释里明写了 `_express` 必须在 `_blinkUpdate` 之后、`_musicTick` 必须在 `_express` 之后）
- 两个手写的时间窗互斥锁：`_exprHoldUntil`（播放模型自带表情时挂起五官）、`_motionHoldUntil`（播放模型动作时挂起躯干/头部）

冲突范围其实已经很清楚了：

| 参数 | 现有写者 | 面捕也要写？ |
|---|---|---|
| `ParamAngleX/Y/Z` | `_idle`（视线基线）、`_musicTick`（点头） | ✅ 要 |
| `ParamEyeLOpen/ROpen` | `_blinkUpdate`、`_express`（乘算）、`_musicTick`（压低） | ✅ 要 |
| `ParamEyeBallX/Y` | `_idle`（视线） | ✅ 要 |
| `ParamBrowLY/RY/LForm/RForm` | `_express` | ✅ 要 |
| `ParamMouthOpenY` | viseme、TTS 响度、待机口型 | ✅ 要 |
| `ParamMouthForm` | `_express` | ✅ 要 |

**六个写者、靠注释维持秩序**。再加面捕就是第七个，而且要抢的正好是最核心的那几个参数。再叠一层 `_faceHoldUntil` 只会让状态机更难推理。

## 三、方向一：面部捕捉

### 3.1 推理方案

**MediaPipe Face Landmarker**（`@mediapipe/tasks-vision`）。选它的理由：

- 浏览器 / Electron 渲染进程直接可用（WASM + WebGL GPU 委托，**不需要 Python 侧车**，不用碰 Electron 里引原生模块的坑）
- 单帧推理 5–15 ms（GPU 委托），够 30 fps
- 官方模型三档：轻量 4.3 MB / 标准 6.2 MB / 高精 10.6 MB（含虹膜）。**建议先上标准版**，眼睛精度不够再换高精
- 一次输出三样东西，正好对应三类参数：
  - **478 个关键点** → 备用（比例、脸宽，做增益归一化）
  - **52 个 blendshape**（ARKit 命名）→ 五官参数
  - **4×4 面部变换矩阵** → 头部姿态（旋转/位移/缩放）

### 3.2 映射表：52 blendshape → Hotaru2024

`_neutral` 忽略，其余 51 个：

| 类别 | MediaPipe blendshape | 目标参数 | 关系 |
|---|---|---|---|
| 眨眼 | `eyeBlinkLeft/Right` | `ParamEyeLOpen/ROpen` | 取反 `1 - blink` |
| 瞪眼 | `eyeWideLeft/Right` | `ParamEyeLOpen/ROpen` | 增益 >1，与上项取大 |
| 挤眼 | `eyeSquintLeft/Right` | `ParamEyeSquintL/R` | **1:1** |
| 颊挤 | `cheekSquintLeft/Right` | `ParamEyeSquintL/R` | 叠加 |
| 鼓腮 | `cheekPuff` | `ParamCheekPuff` | **1:1** |
| 眼球 | `eyeLookUp/Down/In/Out × L/R`（8 个） | `ParamEyeBallX` / `ParamEyeBallY` | 四方向合成后钳位 |
| 眉上 | `browInnerUp` | `ParamBrowLY` + `ParamBrowRY` | 同向 |
| 眉外挑 | `browOuterUpLeft/Right` | `ParamBrowLY/RY` | 正向 |
| 眉下压 | `browDownLeft/Right` | `ParamBrowLY/RY`（负）+ `ParamBrowLForm/RForm`（负） | 拆成"高度 + 形状"两个旋钮 |
| 下颌 | `jawOpen` | `ParamJawOpen`（或 `ParamMouthOpenY`） | **需实测哪个生效** |
| 下颌左右 | `jawLeft` / `jawRight` | `ParamMouthX` | 合成 |
| 嘴漏斗 | `mouthFunnel` | `ParamMouthFunnel` | **1:1** |
| 噘嘴 | `mouthPucker` | `ParamMouthPuckerWiden` | **1:1** |
| 抿嘴 | `mouthPressLeft/Right` | `ParamMouthPressLipOpen` | **1:1** |
| 嘴耸动 | `mouthShrugUpper/Lower` | `ParamMouthShrug` | **1:1** |
| 微笑 | `mouthSmileLeft/Right` | `ParamMouthForm` | 正向 |
| 皱眉嘴 | `mouthFrownLeft/Right` | `ParamMouthForm` | 负向 |
| 嘴左右 | `mouthLeft` / `mouthRight` | `ParamMouthX` | 合成 |
| 嘴角窝 | `mouthDimpleLeft/Right` | `ParamMouthForm` | 弱权重近似 |

**覆盖统计**：约 **30 个直接 1:1**，**16 个近似/组合**，**5 个无对应**（`jawForward`、`noseSneerLeft/Right`、`mouthRollUpper/Lower`）。

⚠️ **一个反直觉的点**：`tongueOut` 是 **ARKit 有、MediaPipe 没有**的。模型提供了 `ParamTongueOut`，但本机摄像头路线驱动不了它——只能在「手机 ARKit 路线」或「手动触发/情绪预设」里用。现有 `EMOTION_PRESETS.tease` 就在用，别删。

### 3.3 头部姿态解算

变换矩阵是 4×4 列主序。做法：

1. 取左上 3×3 旋转部分
2. 抽出欧拉角：yaw / pitch / roll
3. 映射到参数。**注意轴约定**（`live2d-loader.js:607` 已记录）：
   - `ParamAngleX` = yaw = 左右转头
   - `ParamAngleY` = pitch = 低/抬头
   - `ParamAngleZ` = roll = 歪头
4. 默认范围约 ±30°，需可调增益（VTS 里也有这个"角度增益"）
5. **必须先确认 `ParamAngleX` 还是 `ParamAngleX2` 生效**（见 2.3）

### 3.4 校准与滤波（决定"能不能用"的部分）

面捕好不好用，**八成取决于这两块，不是模型本身**：

**校准**（第一次用必须做）：
- 中立位：正视摄像头 3 秒，记录各参数基线值（有人天生抬眉/嘴角下垂，不校准则永远歪）
- 范围标定：咧嘴到最大、睁眼到最大、左右转到底 → 记录上下限做归一化，把每个人的脸映射到 0..1
- 死区：小幅度抖动不驱动参数（防"永远在微动"）
- 增益：每项独立可调

**滤波**：
- 一阶低通（现有代码的 `smooth` 就是这个思路）够用
- 建议上 **One Euro Filter**：静止时稳、快速动作用跟得上位。这是 VTS 那类软件"手感好"的关键
- 眨眼/张嘴这类**快变**要小平滑，头部姿态这类**慢变**可以大平滑

### 3.5 与现有模块的冲突：需要仲裁层

**建议的前置重构**：把"谁写哪个参数、怎么混合"从**注释里的时序约定**改成**一张显式的表**。

概念上大概是：

```
每个参数一个解析规则：
  参数名 → [ (来源, 权重/优先级, 混合方式) ... ]

混合方式至少三种：
  replace  覆盖（高优先级独占，如面捕开启时的头部角度）
  add      叠加（情绪对五官的偏移）
  mul      乘算（音乐对眼睛开合的压低、眼开合统一基线）
```

然后每帧只做一次「收集 → 按规则合成 → 写入」，替代现在"谁后写谁赢 + 两个 hold 窗口"。

**收益**：面捕接入变成"注册一个新来源"，而不是"再插一层 if 和再记一条顺序约束"。同时现有几个偶发问题（模型表情被情绪层吃掉、音乐与眨眼互相覆盖）也有统一解法。

**代价**：要动 `_idle` / `_mouth` / `_blinkUpdate` / `_express` / `_musicTick` 五个函数的写参数方式。**但只是改变组织方式，不改行为**——现有行为可以作为回归基线，用自检脚本比对重构前后的逐帧参数值。

## 四、方向二：把它做成「面捕源」（这才是 VTS 的护城河）

VTS 被人依赖，不只是因为它能驱动自己的模型，而是**它能把跟踪数据发给别人**。桌宠要"像 VTS"，最该补的是输出能力：

| 输出 | 协议 | 用途 | 难度 |
|---|---|---|---|
| **VMC 协议** | UDP，默认 39539，OSC 风格 `/VMC/Ext/Bone/Pos` 等 | 发给 VSeeFace / Warudo / 其他支持 VMC 的软件 | 中（按 VRM 骨骼语义发数据，与 Live2D 参数语义要对一遍） |
| **OSC** | UDP | 自定义用途、给 Unity / TouchDesigner | 低 |
| **WebSocket JSON** | 本机 ws | 给浏览器类工具（包括将来做网页版监视器） | 低 |
| **虚拟摄像头** | DirectShow | 让桌宠画面出现在 Zoom / OBS / 会议软件里 | 高（要装虚拟摄像头驱动，可先用 OBS 的虚拟摄像头转发兜底） |
| **NDI** | NDI SDK | 直播/演播室工作流 | 高（可后置） |

**先做 WebSocket JSON 和 OSC**（几十行），VMC 次之。虚拟摄像头最后——OBS 已经能替代 90% 需求。

另外，**透明窗口 + OBS 窗口捕获** 是"桌宠直播"的最短路径，基本不用写代码，只需要文档教怎么配。这条值得单独写一篇。

## 五、方向三：其他值得加的功能（按性价比排序）

### P0 级（低成本、高感知回报）

1. **人脸出现检测** —— 不做面捕，只做"有没有人"。用系统级的人脸检测或极低频（2 fps）的轻量检测即可。有人坐下 → 她抬头、看你、打招呼；人离开 → 她继续待机。**算力几乎为零，但"她注意到我了"是桌宠最重要的情感反馈。** 与面捕共用摄像头与管线，是面捕的最小可用版本。
2. **系统状态感知** —— CPU / 内存 / GPU / 磁盘 / 网络 / 电池。她已经在播待机台词了，把系统指标接进台词选择条件即可。她会抱怨"电脑今天好烫"、你打游戏时她安静些。**纯读数据，风险极低。**
3. **前台应用感知** —— Windows 拿得到前台窗口标题/进程名。写代码、看视频、打游戏、开会，四种情境给四种反应。"你在开会"时自动闭嘴更是刚需（她现在会随时说话）。

### P1 级（需要额外组件，但价值明确）

4. **语音输入（ASR）** —— 现在只能打字聊天，能"对她说话"是体验断层级的差别。本机已有 cosyvoice / index-tts 的 Python 环境，加 `faster-whisper` 做本地转写即可。链路：麦克风 → VAD 断句 → ASR → 现有 ACP 聊天 → TTS 回话。**这条打通，她才是真桌宠。**
5. **唤醒词** —— 避免一直收音。`openWakeWord` 或 Porcupine（自定义唤醒词"黑叶萤"）。与上一条配套。
6. **长时间无输入时的关心** —— 检测键鼠静默超时（`GetLastInputInfo`），1 小时后她提醒你起来动动。成本极低，情感价值高。

### P2 级（表现力增强）

7. **更多待机动作** —— 现在只有 `idle` / `sleep` 两个 motion（模型自带），表情 12 个。**你有 Cubism Editor 5.3，可以自己用参数曲线做 motion3.json**（不需要重新 rigging，直接给现有参数打关键帧即可）。这是提升"活人感"最直接的投入。
8. **物理参数调优** —— `physics3.json` 存在但看行为像是默认值。头发/兽耳/尾巴/领带的摆动幅度、响应速度调一调，动起来会自然很多。
9. **窗口位置联动视线** —— 拖动窗口时，她的视线跟着屏幕上的位置走（现在视线是相对窗口的）。涉及屏幕追踪模块已有能力，改动小。
10. **语音情绪联动** —— 从 TTS 文本或音频中判断情绪，自动切 `EMOTION_PRESETS`。现在情绪是按台词池的 `emo` 字段硬编码的，可以自动化。

### P3 级（结构性投入）

11. **多角色同屏** —— 两个模型互相说话。架构上需要多实例管理 + 跨实例事件，投入较大。
12. **插件系统** —— 允许用 JS 注册新的"感知源 → 参数"映射与新行为。等仲裁层建好之后，这件事会变得很自然。
13. **番茄钟 / 日程提醒** —— 她有台词系统、有 TTS、有气泡，加个定时器就能当提醒用具。

### Q3 是否接受先做「参数仲裁层」重构？

大约要改 5 个函数的写参数方式。不改行为、可以用自检脚本回归验证，但确实是动核心。**跳过它直接接面捕也能跑，代价是后面每加一个感知源都要多记一条时序约束，最终会失控。**

### Q4 面捕要"抢"哪些参数？

面捕和现有功能会抢同一批参数，需要你定**优先级语义**。比如：

- 面捕开启时，头部角度 / 眼开合 / 嘴型**完全交给面捕**（情绪与口型让位）？
- 还是**面捕只做偏移**（你的真实动作叠加在她自己的情绪表演上）？

这两种手感差别很大：前者像 VTS（你在演她），后者像"她有自己的生命，你的表情会传染给她"。**我倾向于后者更适合"桌宠"定位**，因为它保住了她已经写好的情绪与待机系统。

## 七、风险与代价

| 风险 | 说明 | 缓解 |
|---|---|---|
| **内存吃紧** | moc3 明文 56 MB，当前占用约 2.3 GB，本就出现过 OOM | 面捕本身（WASM + WebGL）额外开销不大，但摄像头帧缓冲 + GPU 委托会加压力。先把摄像头分辨率压到 640×480，再做一次内存基线测量 |
| **GPU 争用** | 渲染与推理共用 WebGL | MediaPipe 用独立 WebGL 上下文；必要时降推理帧率到 15–20 fps（面捕不需要 60 fps） |
| **摄像头隐私** | 常开摄像头 | 明确的状态指示（托盘图标变色）、一键关闭、不落盘任何画面 |
| **模型兼容性** | 映射表是按 Hotaru2024 写的 | 映射表要做成**按参数名探测**（现有 `_hasParam` 已是这个思路），缺参数的模型自动降级 |
| **Electron 摄像头权限** | 需要 `setPermissionRequestHandler` 放行 | Windows 上无需额外声明；macOS 版要补 `NSCameraUsageDescription`（会同时影响已发布的 mac 包） |

## 八、如果只做一件事

**买/接一个摄像头，然后只做「眨眼 + 张嘴 + 头部姿态」这三项。**

理由：这三项就能让"她"从"播放动画"变成"看着你、跟着你动"，是感知收益最大的一步；而且它**不需要**先做仲裁层重构（可以先用"面捕开启时独占这几个参数"的简单策略验证手感），也不必写映射编辑器、校准向导、输出协议。

**先验证手感值不值得投入，再决定要不要重构成一个正经的面捕软件。**
