# 方案 · 把黑叶萤做成 AI 主播（Neuro 式）

> 起因：既然桌宠已经能对话、能发声、能做表情口型，那能不能做成 Neuro-sama 那样的 AI VTuber？  
> 本文给可行性判断、现状盘点、架构、里程碑与风险。**结论先行，依据在后。**

---

## 一、结论

**可行，而且比想象的近** —— 但需要认清「近」的是哪一半。

- **已经有的是「半个身子」**：形象、发声、情绪、口型、人格、对话，这五件事本项目都已建成并实测过  
  （细节见第三节的对照表）。Neuro 那种"看起来是活的"里，**表现层**的部分你大概完成了七到八成。
- **缺的是另一半：直播的工程部分**。三件必须新建的东西 ——  
  **① 句子级流水线（把延迟压到 1 秒出头）、② 导演循环（决定"现在该说什么"，而不是等输入）、  
  ③ 弹幕接入与直播输出**。这三件都不是模型问题，是系统问题，也正是 Neuro 真正难的地方。
- **不要指望"复刻 Neuro"**。Vedal 那套是长期调教 + 一整个 agent 工程 + 游戏专用感知/操作层叠出来的，  
  而且她好看的很大一部分来自主播本人的互动设计与直播节奏。**我们能做的目标应该是：  
  "一个能自己起话头、会读弹幕、反应够快、人格稳定" 的 AI 主播**，这条路是工程问题，不是研究问题。
- **唯一可能否决整个方案的技术点只有一个：TTS 首句延迟**。它现在是整条链上最慢、也最没被量过的一环  
  （见第四节）。**先量它，再决定往下投入多少。**
- **可以做成纯本地的**（补充结论，见第八节）：M0 / M1 / M3 零外部依赖，M2 里只有「真实弹幕源」必须联网；
  而且本机现在就已经是纯本地 TTS 配置。纯本地还顺带消掉了成本、断网、内容外传三条风险。

## 二、和 Neuro 的差距，拆成能力维度看

| 维 度            | Neuro 的水平    | 本项目现状                                             | 判断            |
| -------------- | ------------ | ------------------------------------------------- | ------------- |
| Live2D 形象与渲染   | 定制模型 + 精修绑定  | 多模型可换、透明置顶窗、拖动缩放                                  | **够用**        |
| 参数驱动（眨眼/视线/头身） | 精细           | 鼠标 + 屏幕运动追踪驱动视线，呼吸/摆头待机                           | **够用**        |
| 口型同步           | 音频级          | **音频 RMS 驱动** + 文本拼音/假名兜底                         | **够用**        |
| 情绪表现           | 大量表情与动作      | 13 种情绪 → 参数映射；模型原生 exp3/motion 可绑触发器              | **够用**        |
| 声音             | 定制/微调音色      | 4 类引擎（Edge/CosyVoice/IndexTTS/SAPI）+ 按语言音色 + 情绪标签 | **缺情绪细腻度，可用** |
| 人格设定           | 精心写就 + 长期调教  | persona.json（种族/外貌/性格/语气/边界）+ 提示词铁律               | **够用**        |
| 对话能力           | 定制模型         | 三选一后端（本地/云端/WorkBuddy），流式输出、可中断、超时保护              | **够用**        |
| **反应延迟**       | 亚秒级          | **整段生成 → 整段合成 → 解码后才出声**，长句 3~8 秒                 | **必须重做**      |
| **主动性/自主行为**   | 自己找话题、接梗、玩游戏 | 只有"随机挑固定台词"的定时器                                   | **必须新建**      |
| **弹幕/观众感知**    | 实时读弹幕、认人、记梗  | 无                                                 | **必须新建**      |
| **记忆**         | 长期记得观众与梗     | 只保留本场对话，刷新即丢                                      | **必须新建**      |
| **直播输出**       | 场景/字幕/多路音频   | 透明置顶窗，直接捕获会带上桌面背景                                 | **必须新建**      |
| **长时间稳定性**     | 数小时连播        | 未做过压测；历史上出现过 OOM                                  | **未知，需验证**    |

一句话：**表现层已经能用，系统层基本空白。**

## 四、先量一件事：端到端延迟预算

目标必须定死，否则做出来会觉得"哪儿都对但就是不像活的"：

- 「决定要说」→「出声」**< 1.2 秒**
- 「弹幕到达」→「出声」**< 2.5 秒**（其中要留 100~200ms 攒批去重）

| 环 节          | 现状实测                          | 目标           | 备注                 |
| ------------ | ----------------------------- | ------------ | ------------------ |
| 弹幕 → 文字      | 无                             | 20~200 ms    | WebSocket 直连       |
| 攒批 / 去重      | 无                             | 50~200 ms    | 需要，否则逐条回会碎         |
| LLM 首 token  | **本地热态 33 ms**（已实测）；冷启动 53 s  | < 300 ms     | 冷启动必须靠预热解决，直播里不能出现 |
| LLM 首句完成     | 本地短句 **总耗时 203 ms**（已实测）      | < 600 ms     | 7B 热态表现比预期好        |
| **TTS 合成首句** | **从未测过**                      | **< 700 ms** | ← **决定性未知**        |
| 音频解码 + 起播    | 现在是"整段下载 + `decodeAudioData`" | < 100 ms     | 首句切短后代价很低          |
| 口型/表情起效      | 音频 RMS，近实时                    | —            | 已有                 |

现状端到端 = 整段 LLM + 整段 TTS + 整段解码，所以**越长的回答越像卡住**。

### 4.1 改法：句子级流水线

```
LLM 流式输出 ──按句切──▶ 句子队列 ──▶ TTS(第1句) ──▶ 播放
                              │                        │
                              └──▶ TTS(第2句) ────────┘  ← 第一句还在播时，第二句已在合成
```

要点：

1. **按句切**，不是按 token。中文按「。！？…」+ 逗号兜底，超过 N 字强制切。
2. **首句优先**：第一句往往最短（"不是吧——"），起播最快，观感提升最大。
3. **不吃掉情绪标签**：标签在句首，切句时要把 emo 留在队列项上（现有 `createTagStripper` 可直接用）。
4. **一条音频在播时，后面的先排队**；高优先级可抢占（见 5.2）。
5. **不做流式 WAV 也能达标**：`/tts` 是按句调用的，引擎不用改；如果测下来首句仍慢，再考虑流式合成。

### 4.2 双脑分层（建议）

- **快脑 = 本地 Ollama（热态）**：负责"短反应"——吐槽、附和、被叫到名字的回一句。33ms 首 token 是巨大优势。
- **慢脑 = 云端**：负责需要记性和推理的回合——读弹幕长问题、总结、接梗、写话题。
- 路由规则很简单：**预计输出短 + 需要快 → 快脑；需要上下文/长文 → 慢脑**。  
  由导演循环在发起前决定，命中不准就退化成"两个都用、谁先到用谁"。

### 4.3 语音引擎的选择（**纯本地路线以本地引擎为主**）

项目里已有 5 个引擎，**本地 / 联网的界线很清楚**（见 `tts/engines.py`）：

| 引擎 | 位置 | 定位 | 联网 |
|---|---|---|---|
| `cosyvoice` | 本地 `D:\cosyvoice_src` | 注释写明「**实时流式**用途（聊天回复）」 | 不联网 |
| `indextts` | 本地 `D:\index-tts`（权重 `checkpoints_2` 已就位） | 离线最佳音质 + **情感/音色分离** | 不联网 |
| `sapi` | Windows 内置 | 零下载兜底 | 不联网 |
| `tone` | 本地纯 Python | 占位提示音 | 不联网 |
| `edge` | **微软在线服务** | 音色优于 sapi | **需要联网** |

优先级 `cosyvoice > indextts > edge > sapi > tone`，本机 `ttsEngine` 已设为 **cosyvoice**。

- **实时档（说话）→ CosyVoice 本地**：官方定位就是流式实时，先跑通它。
- **质量档（预生成台词）→ IndexTTS 本地**：音质最好但慢，适合提前批量生成。
- **兜底 → SAPI 本地**：本地模型起不来时至少还能出声，纯本地方案必须留这个保险。
- **Edge 只在允许联网时作为补充**，不参与纯本地路线。

> ⚠ **一个必须注意的实现细节**：`cosy_gen.generate_best(cosy, text, max_candidates=8, …)`
> 做的是**多候选选优 + 伪影硬拒绝 + 响度归一**，天然要拿到整段音频才能工作 ——
> 也就是说**底层模型支持流式，但当前这条路径不是流式的**。
> 好在旋钮已经预留：代码注释写着「预生成用 8（充分选优）；**聊天实时用 1~2（快）**」。
> 实时档走 `max_candidates=1~2` 的快路径；要更极致再考虑直连底层流式接口。

## 五、要新建的三块

### 5.1 `app/js/director.js` —— 导演循环（最关键）

它决&#x5B9A;**"现在要不要说话、说什么"**，是"像活的"和"像个问答框"的分界线。

```
                    ┌─────────────── 事件总线 ───────────────┐
  弹幕 / 礼物 ──────▶                                        │
  屏幕运动 ────────▶       ┌──────────────┐                 │
  音乐节拍 ────────▶       │  导演循环     │──▶ say(text, emo, priority, ttl)
  定时器 ──────────▶       │  (每 1~2s)   │──▶ act(motion/expression)
  上一条自己的话 ──▶       └──────┬───────┘──▶ think(topic)  ── 更新话题栈
                                  │
                          话题栈 + 短期摘要 + 人设
```

- **输入**：归一化事件（`{type, text, who, ts, salience}`）。
- **输出**：`say / act / think / silence` 四种之一。
- **实现**：每 1~2 秒一次极短的决策调用（**让它输出结构化 JSON 而不是自由文本**：  
  `{"speak": "...", "emo": "tease", "action": null}`），空回复就代表"这条跳过"。  
  决策用快脑，成本极低（几十个 token）。
- **话题栈**：把"正在聊什么"显式存下来，避免每轮都重新起话头（这是最像"失忆"的地方）。
- **节流**：同一条弹幕只回一次；同一话题连续 3 轮没推进就换。
- **兜底**：决策超时/失败时，退化为现在的随机待机台词 —— **保证永远不静默**。

### 5.2 说话优先级与抢占（避免叠音、避免被刷屏打断）

| 优先级 | 来源            | 行为                |
| --- | ------------- | ----------------- |
| 3   | 主播本人指令 / 高额礼物 | **立刻打断**当前语音，先回应  |
| 2   | 直接提问（含"萤"等称呼） | 排队到当前句播完          |
| 1   | 普通弹幕          | 攒批合并，合并后仍超量则丢弃低分项 |
| 0   | 自说自话 / 待机台词   | **只要有更高优先级就立刻让位** |

现有代码里已经有一条经验可沿用：`_tryIdleLine` 的"正在说话就稍后重试"。  
但直播版必须升级为**真队列 + 抢占**，并明确"被抢占的话是否记住（下次接回来）"。

### 5.3 直播输出（`app/live.html` + 场景）

现在的窗口是**透明 + 置顶**，直接窗口捕获会把桌面一起播出去，所以需要一个直播专用渲染页：

- 固定画幅（例如 1280×720 / 1920×1080）、不透明背景或绿幕色、可选透明（给 OBS 色键）。
- 分区：主舞台（模型）+ 字幕条（当前说的话，含情绪色）+ 可选状态角标（当前话题/正在听的弹幕）。
- 供 OBS 用**浏览器源**捕获（比窗口捕获稳定，且不受 Windows 缩放影响）。
- 音频：TTS 走**虚拟音频设备**（如 VB-CABLE），一路给直播、一路不打扰自己。
- 现有 `screen-debug.html` 的实时曲线与 `music-debug.html` 的状态机面板，  
  可以直接改造成「主播调试面板」：显示事件流、当前话题、说话决策与队列 —— **直播排障全靠它**。

### 5.4 记忆（先做便宜的）

- **短期**：本场对话 → 滚动摘要（每 N 轮压一次），进提示词。
- **长期**：观众档案（昵称 → 印象/梗）、人设档案、名场面。落 `jsonl` 追加文件 + 简单关键词检索即可，  
  **先不要向量库**（收益小、维护成本高）。
- 提醒：项目里已有「人设不因为上下文丢失而漂移」的提示词铁律，记忆层要复用这个思路。

## 六、里程碑（按"做完能看到什么"划分，不排工期）

### M0 · 量延迟 —— ✅ **已完成（2026-09-22），结论见 [`M0-语音引擎测量.md`](./M0-语音引擎测量.md)**

**出口判据「首句 < 700ms」没有通过，而且差得远。实测结果：**

| 引擎 | 能用你的音色 | 单句耗时 | RTF | 判定 |
|---|---|---|---|---|
| CosyVoice（本机默认） | ✅ | **12~100 s**（含 ~12 s 固定地板） | 3.0~6.9 | 不能实时 |
| IndexTTS | ✅ | **385 s**（短句！） | 115~157 | 不可用（装不下显存） |
| SAPI（对照） | ❌ | 1.3~1.6 s | 0.08~0.56 | 实时、确定性 |

三条关键结论（细节与全部原始数据在报告里）：

1. **CosyVoice 每次推理有一个约 12 秒的固定地板，与句子长短无关** —— 说一句"嗯"也要等 12 秒。
   已排除 GPU（fp16 43.7 TFLOPS 健康）、torch（cu118）、显存、`empty_cache`、后处理（只占 4~9%）；
   94~96% 的时间在模型推理里。剩下最可疑的是 `load_jit=False/load_trt=False` 与注意力落到慢分支。
2. **"只用一个引擎"还不够** —— 同一引擎、同一句话合成 3 次，音高漂 **2.75 半音**、语速差 **70%**。
   根源是没有固定随机种子 + 每次都换 speed 网格。要"不变声"必须**固定随机源**。
3. **因此本阶段的路线改为「预生成 + 缓存」为主**（详见报告第七节）：
   固定话术全部离线预生成成文件，运行时直接播 —— 延迟≈0、且同一句永远同一个文件，**变声期从根上消失**。
   CosyVoice 的 12 秒地板则作为一个独立的排查项（若压到 1 秒内，才有资格谈"真实时"）。

顺带：**本轮还挖出并修掉了两个让 `cosyvoice` 引擎完全无法出声的 bug**，其中一个已随 v0.2.2 的安装包发出 ——
详见报告第三节。

### M1 · 会自己说话的主播（**最能验证"像不像活的"**）

- 新建 `director.js`：事件总线 + 话题栈 + 决策 JSON + 优先级抢占。
- 事件源只用**已有的**两个：屏幕运动追踪（有人在动）、音乐节拍（在放歌）。
- 端到端改造：决策 → LLM 流式 → 句子流水线 → 播报 → 口型/表情。
- **做完的观感**：没人理它时它会自己看向屏幕并评论；你在放歌它会跟着说两句；  
  你打字打断它，它会停下让位。**不需要弹幕、不需要记忆就能看出成色。**

### M2 · 接一个平台的弹幕 + 记忆

- 主进程加弹幕适配层（WebSocket → 归一化事件 → 渲染进程），**先只做一个平台**。
- 观众/人设档案 + 本场滚动摘要；"认人"与"接梗"。
- 完成标准：能读弹幕回答问题、能记住本场说过的梗、刷屏时不会崩。

### M3 · 直播输出与稳定性

- `live.html` + OBS 浏览器源 + 字幕条 + 虚拟音频设备路由。
- **8 小时压测**：内存、TTS 队列漂移、模型显存、窗口/浏览器源掉帧。
- 完成标准：能真的开一场播，中途不需要人看着。

### M4 · 半自主内容（可选）

- 玩游戏/看图说话/调工具：可以复用现有的 WorkBuddy ACP 桥接（能读写本地文件、调工具），  
  或接具体游戏的状态接口（比"看画面猜"靠谱得多）。
- 这一层才是真正接近 Neuro 的部分，**建议等前三步稳了再评估**。

## 七、风险与合规（必须提前想）

1. **稳定性**：连续数小时的进程，任何"慢慢泄漏"都会在 2 小时后爆发。  
   本项目有过 OOM 记录 —— M3 的压测不是可选项。
2. **内容安全**：直播里说出不当内容的风险是实打实的，本地小模型更容易跑偏。  
   需要输出过滤（关键词 + 一次快速复核调用）+ 一键切断（终止当前语音/清空队列）。
3. **平台合规**：主流平台要求对 AI 生成内容做标注；直播场景下还要注意  
   **不要让它冒充真人**。这条要在开播前就确认清楚，不是上线后再补。
4. **声音授权**：仓库里已有声纹参考样本（`.gitignore` 已刻意排除）。  
   如果音色来自他人，**商用/公开直播是另一回事**，必须取得许可。
5. **成本**：云端 API 按 token 计费。长时间直播要设日/场上限与熔断（超预算自动降级到本地）。
6. **观感预期管理**：Neuro 的魅力有相当一部分来自主播的互动设计。  
   **技术做完只是"能播"，好不好看取决于内容和节奏设计。**

## 八、纯本地可行性：哪些环节必须联网

**结论：M0 / M1 / M3 可以做到 100% 本地；M2 里只有「真实弹幕/礼物源」必须联网；
M4 取决于具体游戏。** 而且**本机当前本来就是纯本地 TTS 配置**（`ttsEngine = cosyvoice`，
CosyVoice 源码在 `D:\cosyvoice_src`、IndexTTS 权重在 `D:\index-tts\checkpoints_2`、
环回采集 `audio/audio_server.py` 零网络依赖）。

### 8.1 逐环节清单

| 环节 | 外部依赖 | 是否可本地替代 | 本地替代方案 |
|---|---|---|---|
| 大脑（LLM） | 云端 API（可选） | **可** | 本地 Ollama（已在用，热态首 token 33ms） |
| 语音合成 | Edge TTS（**在线**） | **可，且已是本地方案** | CosyVoice（本地流式）/ IndexTTS（本地离线）/ SAPI（兜底） |
| 屏幕视觉 | 无 | **本来就地** | `desktopCapturer` 截屏 + 本地运动检测（已在用） |
| 听声音/节拍 | 无 | **本来就地** | WASAPI 环回采集（已在用） |
| 记忆 | 无 | **本来就地** | 本地 jsonl + 关键词索引 |
| 说话调度 | 无 | **本来就地** | `director.js`（新建，纯本机进程） |
| 直播画面输出 | 无 | **本来就地** | 本地 `live.html` + OBS **浏览器源**（抓 `127.0.0.1`） |
| 音频分路（一路给直播） | 虚拟声卡驱动（可选） | **可** | Win10 2004+ 的 **「应用程序音频捕获」**（按进程抓，不装驱动）；退一步用声卡的「立体声混音」 |
| 录播 / 推流闭环 | RTMP 平台（仅在对外开播时） | **可** | 录制到本地文件；或推到**本地 RTMP**（MediaMTX / nginx-rtmp）做全链路自测 |
| **真实弹幕 / 礼物** | **平台 WebSocket（必须联网）** | **不可替代** | 但可用三类本地源先跑通：① 本地注入台（自己敲"伪弹幕"）② 本地文件回放 ③ 本地模型扮演"虚拟观众" |
| 工具调用 | 无 | **本来就地** | WorkBuddy ACP 是 `127.0.0.1` 本地端口，不算外网 |
| 玩游戏（M4） | 视游戏而定 | **多数可** | 有本地接口的：Minecraft RCON / osu! / 模拟器存档内存；纯画面理解：本地 VLM（可行但吃显存、慢） |

### 8.2 一个容易混淆的点：联网 ≠ 开端口

整个方案**不需要公网 IP、不需要服务器、不需要开放任何入站端口**。

- 进程之间全是本机 `127.0.0.1`（静态服务 18765、TTS 侧车 18766、Ollama 11434、ACP）。
- 即使接弹幕，也是**出站** WebSocket（你的程序主动连平台），不是别人连你。
- 只有「真的对外开播」这一步需要平台给的推流地址 + 密钥。

### 8.3 纯本地的真实代价（要认下来）

1. **显存/算力竞争（最硬的一条）**：本地 LLM（7B q4 约 5~6 GB）+ 本地 TTS（CosyVoice/IndexTTS 也要 GPU）
   + Live2D 渲染同时抢。**上线前必须先实测共存**；不够就只有两条路：
   ① 缩小 LLM（3B）或把 TTS 放 CPU；② 错峰（只在需要出声时占 GPU）。
2. **语音要分两档用**：IndexTTS 音质最好但慢（适合预生成），CosyVoice 快但要多调
   （实时档 `max_candidates=1~2`）。不是"哪个更好"，是"哪档用在哪儿"。
3. **互动感的来源变了**：没有真人弹幕，"谁在看"这件事得自己造 ——
   虚拟观众、屏幕吐槽、你本人打字。**这不是技术问题，是内容设计问题**，也是纯本地方案最需要想清楚的一环。
4. **LLM 能力上限**：全本地就要接受 7B 档的人格稳定性与长上下文能力，无双脑兜底（4.2 里的"慢脑=云端"退化为
   "慢脑=本地更大模型"或直接取消分层）。
5. **顺带的好处**：断网可用、零 API 成本、聊天内容不出本机 —— 我上一版风险表里的
   「成本熔断」「断网降级」「内容外传」三条**同时消失**。

### 8.4 因此建议的路线（纯本地优先）

```
M0  本地引擎计时（CosyVoice 实时档 vs 预生成档的差距）      ← 仍先做这个
M1  纯本地自主说话（屏幕 + 音乐事件，无弹幕、无记忆）        ← 零外部依赖
M2' 本地伪弹幕源 + 记忆（本地注入台 / 虚拟观众，接口按平台弹幕的形状设计）
M3' 本地录播闭环（live.html + OBS 浏览器源 + 本地推流自测）  ← 零外部依赖
M2  接平台弹幕（只换适配器，核心不动）                      ← 唯一的联网点
M3  对外开播（推流地址 + 密钥，并确认平台的 AI 标注要求）
```

**关键设计约束**：把「事件源」做成**适配器接口** —— 本地伪弹幕与平台弹幕是同一个接口的两个实现。
这样核心（导演循环、流水线、记忆、输出）**一行都不用为联网改造**，将来接平台只加一个文件。

## 九、我的建议

**先做 M0 的测量，不要先写 M1 的代码。** 理由是：整条方案的成败卡在"TTS 首句有多快"这一个数字上，
而它现在完全是空白。如果首句能做到 400~700ms，M1 会非常顺；如果所有引擎都要 2 秒以上，
那必须先解决引擎（走实时档 / 直连流式接口 / 上 GPU 常驻），否则流水线做得再漂亮也救不回来。

**而且这个测量要按"纯本地"来做**（见第八节）：主测 **CosyVoice 本地实时档**，
对照 **IndexTTS 本地**（质量/延迟的取舍），**SAPI 本地**作可用性兜底。
Edge 只在联网时作参考，不作为纯本地路线的依据。

需要的话，下一步我可以直接把 M0 做掉：写一个测量脚本，对上述本地引擎逐句测首字延迟与总耗时，
输出一张数字表；顺手把"按句流水线"的骨架搭出来做对照实验。
