# 黑叶萤桌宠 · 功能扩展方案

> 本文只讨论桌宠自身可扩展的功能，不含面部捕捉（面捕部分见《方案-面部捕捉与功能扩展.md》）。
> 所有结论均基于对现有代码与加密模型资源的实际解析，已标注证据位置，便于核对。

---

## 一、结论摘要

1. **最大的机会不是加新功能，而是把模型里已经存在、但一个都没启用的资源接上。** 模型自带一套完整换装系统（12 个物品开关）、4 个钟表指针参数、32 个可独立控制的部件，而 `config.json` 的 `expressions` 是空数组、`assets.bindings` 只有 1 条演示绑定。
2. **桌宠真正的短板在感知层，不在表达层。** 目前只有两个环境输入（音乐律动、屏幕运动），输出侧却已经很丰富（动作、口型、情绪、视线、物理）。她"能表达"但"不知道发生了什么"。补上时间、在场、前台应用三类感知，体感提升最大。
3. **有一个别人做不了的功能你应该做**：启用 Agent 任务可视化。你的桌宠是国内少见的接了 ACP 的——WorkBuddy 在跑长任务时她可以有"在工作"的表现，这是纯桌宠做不到的差异化。

## 三、第一档：把模型自带的东西用起来

这一档的共同特点：**能力通道已经写好，只差配置数据**，多数改动量在几十分钟到半天。

### 3.1 换装系统（最高性价比）

模型的「物品开关」组有 12 个参数，全部是服装与道具：

| 参数 | 名称 | 对应表情文件 |
|---|---|---|
| `Param109` | 外套 | `Coat` |
| `Param189` | 紧身衣 | `bodysuit` |
| `Param190` | 白衬衫 | （无表情文件，需手配） |
| `Param172` | 鞋子 | `Shoes` |
| `Param108` | 换手 | `changehand` |
| `Param107` | 狙击枪 | `SnipingRifle` |
| `Param184` | 手枪 | `Handgun` |
| `Param171` | 兔子 | `rabbit` |
| `Param194` | 脸红 | `shy1` |
| `Param195` | 脸红2 | `shy2` |
| `Param191` | 晕眩眼 | `dizzy` |
| `Param196` | 唾液 | `saliva` |

配套的 `Parts` 里也能看到实物：`外套前`、`外套后`、`白T恤`、`紧身衣`、`白丝`、`第一套`、`第二套`、`眼镜`、`手枪`、`狙`、`兔子`、`大号钟表`。

**通道现状**：表情播放链路是完整通的，只是没有数据。

```
config.assets.bindings
  → app.js:401 loadBindings()
  → app.js:410 playBinding()          // kind !== 'motion' 时走 playExpression
  → live2d-loader.js:1538 playExpression(name, holdMs)
  → model.expression(name)             // pixi-live2d-display
```

触发点也现成：`onClick` / `onIdle` / `onLine` / `hotkey`（`app.js:426-433`），全局热键由 `main.js:2063` 注册。

**做法（分两步）**

第一步，纯配置验证。往 `config.json` 的 `assets.bindings` 里加 12 条：

```json
{
  "id": "wear-coat",
  "label": "外套",
  "kind": "expression",
  "target": "Coat",
  "holdMs": 300,
  "hotkey": "Alt+C",
  "onClick": false,
  "onIdle": false,
  "onLine": "off",
  "lineRefs": []
}
```

`holdMs` 要设小（300ms）。原因：`playExpression` 的 hold 窗口是给情绪层用的——它会在窗口期内挂起情绪对五官的写入（`_exprHoldUntil`）。物品开关参数（`Param109` 等）情绪层不碰，所以窗口设小不会让开关失效，但能避免无谓地压制情绪 3 秒。

第二步，再加一层持久开关。物品开关和"瞬时表情"性质不同，用 `expression()` 表达语义不清晰（它是"设置并保持"，不是"播放一次"）。建议在 `live2d-loader.js` 加一个专门通道：

```js
// 物品开关：直接写参数并持久保持，不占用表情的 hold 窗口
setItemToggle(id, on) {
  const core = this.model && this.model.internalModel && this.model.internalModel.coreModel;
  if (!core) return false;
  const v = on ? 1 : 0;
  core.setParameterValueById(id, v);
  return true;
}
```

然后 `app.js:410 playBinding()` 里加 `kind === 'toggle'` 分支。这样做的好处是换装状态可以存进 `config.json`，重启后保持（现在 `expressions` 一重启就没了）。

**加分项**：换装是做「好感度解锁」最自然的载体——见 5.2。

### 3.2 表情特效

`脸红`、`脸红2`、`晕眩眼`、`唾液` 这 4 个走现有 `playExpression` 就够，它们本来就是瞬时特效。建议直接接到**情绪系统**上：

- 情绪进入「害羞」→ 播 `shy1`，4 秒后淡出
- 收到长任务 → 播 `dizzy`
- 被连续点击 5 次 → `saliva`（配合台词档案里的 affectionate 人设）

这类"情绪 → 表情"的映射可以做在情绪层内部，不需要新增通道。

### 3.3 时钟报时（本次的意外发现）

`Parts` 里有 `表`（Part10）和 `大号钟表`（Part11），并且参数组里有独立的「齿轮动画」：

| 参数 | 名称 |
|---|---|
| `Param118` | 大齿轮旋转 |
| `Param119` | 小齿轮旋转 |
| `Param120` | 时针旋转 |
| `Param121` | 分针旋转 |

**时针和分针可以独立控制角度**，而且这四个参数**没有出现在任何物理组的输入里**（67 个物理组的输入只有 `ParamAngleX2/Y2/Z2`、`ParamBodyAngleX2/Y2/Z2`、眉毛变形、眼开闭这几个）——也就是说不会被物理或情绪覆盖，可以安全地按时钟逻辑写。

**能做的功能**：

- 她身上的表盘显示**真实时间**（每分钟更新分针，每小时更新时针）
- 整点报时：指针归位 + 齿轮转动 + 一句台词「已经 X 点了」
- 结合"时间感知"（4.1），深夜时指针也可以当作熬夜提醒的一部分

**前提**：需要先实测这四个参数的值域。`cdi3.json` 不带 min/max，得查 `moc3` 或直接写值截图对比。这是个半小时能做完的探针。

### 3.4 大小变 / 腿脚扭正

「其他开关」组里还有 3 个未使用的参数：

| 参数 | 名称 | 可能的用途 |
|---|---|---|
| `Param197` / `Param198` | 大小变 | 角色缩放到小人形态（`change` 表情写的就是 198） |
| `Param146` | 腿脚扭正 | 修正坐姿/躺姿时的腿部姿态 |

`大小变` 很适合做「迷你模式」：占屏更小、可以放在任务栏上方。比缩窗口更自然，因为是真的换了姿态而不是拉伸像素。

### 3.5 分部位点击

**现状**：`model3.json` 的 `HitAreas` 是空数组，`LipSync` 组也是空的。所以现在的点击是**整窗点击**——摸头、戳脸、拉手没有区别。

**三个方案**：

| 方案 | 做法 | 成本 | 精度 |
|---|---|---|---|
| A. 归一化坐标 | 按点击位置在窗口内的比例分区（头 0–0.25、身 0.25–0.6、腿 0.6–1.0） | 极低 | 粗 |
| B. 部件包围盒 | 用 Cubism Core 取 `Part3 头`、`Part13 身体`、`Part43/44 手` 的 drawable 顶点范围，算包围盒后命中 | 中 | 高 |
| C. 注入 HitAreas | 在 `main.js:856 injectModelAssets()` 时补 `HitAreas` 字段 | 中高 | 高 |

推荐 **A 起步、B 升级**。方案 C 虽然最"正规"，但需要确定 HitArea 的坐标，而模型文件是加密的、坐标又依赖于画布尺寸，不如 B 直接用运行时顶点数据来得实在。

顺带一提：`injectModelAssets()` 是个很有价值的切入点——它在模型加载时改写 `model3.json`。除了 `HitAreas`，还能补 `Groups.LipSync`（现在是空的），让口型同步走标准通道而不是靠 `vowelParamFamily: auto` 猜。

### 3.6 待机主动搭话

`config.json` 里 `idleLinesEnabled: false`，代码是 `app.js:74 idleOn = CONFIG.idleLinesEnabled !== false`。

**也就是说"她会主动说话"这个能力已经完整实现，只是被关掉了。** 现在打开就能用：`idleLineMin: 14000` / `idleLineMax: 38000` 的间隔已经配好，40 段中/日语音也已经生成。

建议不要直接打开，而是**先加条件再说**——否则她会在你开会、全屏、深夜不停说话，这是主动搭话最容易翻车的地方。所以这一项的实际依赖是 4.1（时间）和 4.3（前台应用）：

```
主动说话条件 = 已开启
            && 未处于全屏/会议/演示状态
            && 距上次交互 > 阈值
            && 符合当前时段（深夜降频、工作时降频）
            && 随机命中（避免机械感）
```

## 四、第二档：补上感知层

这一档改动量中等，但**情感回报最高**。判断依据：桌宠"活着"的感觉来自"它对正在发生的事有反应"，而不是来自它能做多少动作。

### 4.1 时间与作息

**现状**：完全没有。代码里没有任何时间相关的分支。

**能做的**：

| 场景 | 表现 |
|---|---|
| 早上第一次见面 | 「早上好」+ 伸懒腰动作 |
| 午休 | 提醒吃饭 |
| 深夜（23:00 后） | 打哈欠、指出时针、催睡觉 |
| 周末 | 赖床、待机动作换成更慵懒的 |
| 长时间工作未休息 | 拉袖子提醒 |
| 节日 / 纪念日 | 特殊台词（复用现有人设档机制） |

**实现**：新增 `app/js/time-awareness.js`，暴露 `getPeriod()`（早晨/上午/午间/下午/傍晚/深夜）和一个定时器。台词侧的接入点很现成——`app/data/lines/profiles/*.json` 已经是按人设分档的结构，只要给每条台词加一个 `when` 字段（时段、星期、节日）。

**已有资源可复用**：40 段预生成语音（`click_cn/jp_00-09`、`idle_cn/jp_00-09`）里本来就有一批适合按时段分发的。

### 4.2 在场感知（成本最低、体感最强）

**现状**：`powerMonitor` 与 `getSystemIdleTime()` 在 `main.js` 中完全没有被引用。

**能做的**：

```
键鼠空闲 3 分钟   → 打哈欠、视线开始飘
键鼠空闲 10 分钟  → 切到 sleep 动作（模型已有 sleep.motion3.json）
键鼠空闲 30 分钟  → 完全睡着，呼吸变慢
键鼠恢复活动      → 醒来、看向鼠标、问候语
```

**为什么值得先做**：`sleep.motion3.json` 已经在模型里，`modelAssets` 也早就配了 `sleep` 组。也就是说"睡觉"这个能力是**现成的**，缺的只是"什么时候该睡"的判断。一个 `setInterval` 轮询 `powerMonitor.getSystemIdleTime()` 就能解决。

而且"你离开时她睡着、你回来时她醒了"是桌宠最重要的情感反馈——它传达的是"她在等你"。

### 4.3 前台应用感知

**现状**：无。

这是**桌宠最常见抱怨的解药**——"她挡着我、她在我开会时说话"。

| 前台状态 | 表现 |
|---|---|
| 全屏应用 / 游戏 | 躲到角落、降低透明度、停止主动说话 |
| 会议软件（Teams / Zoom / 腾讯会议 / 飞书） | 禁用 TTS 与音效、静音待机 |
| IDE / 终端 | 安静模式，不主动打断 |
| 浏览器 / 桌面 | 正常活跃 |
| 锁屏 | 相当于"不在场"（配合 4.2） |

**实现**：Windows 侧可用 `GetForegroundWindow` + `GetWindowRect` 判断是否全屏（`win32` 或原生模块）。但要避免引入 node-gyp 编译的原生依赖——**可以复用现成的能力**：你已经有 `desktopCapturer` 取屏幕源（`main.js:1655 pet:getScreenSources`）和 `screen-tracker.js`。更轻量的做法是用 Electron 自带能力做"进程名 + 窗口尺寸"判断。

如果不想碰原生模块，还有个零依赖方案：定时抓一帧低分辨率屏幕（复用 `screen-tracker.js` 的降采样逻辑），统计**画面主导色与变化率**，可以区分"全屏游戏"和"桌面"——不够精确但零成本。

### 4.4 系统负载感知

**现状**：无。

这个方向和你的实际处境高度相关——**你刚遇到过 OOM**（转换 STIL 文件时内存不足）。

| 指标 | 她的反应 |
|---|---|
| 内存占用 > 85% | 捂头、不安，台词「有点喘不过气…」 |
| CPU 持续满载 | 出汗、风扇声效、动作变慢 |
| 电量 < 20%（笔记本） | 提醒充电、昏昏欲睡 |
| 磁盘将满 | 提醒清理 |

**实现**：`os` 模块直接给 CPU 负载与内存，零依赖。电量用 `powerMonitor.getCurrentThermalState()` / 系统 API。**这是成本最低的一档感知**——`os.totalmem()` / `os.freemem()` / `os.loadavg()` 三行就有数据。

### 4.5 其他可选感知源

| 感知源 | 用途 | 成本 |
|---|---|---|
| 剪贴板 | 复制长文本 → 「要我帮你翻译/总结吗」 | 低（`clipboard` 模块） |
| 网络状态 | 断网时提醒；网络恢复时告知 | 低 |
| 系统通知 | 把通知以她的口吻转述 | 中 |
| 麦克风环境音量 | 检测"你在说话"→ 静音倾听姿态 | 中（已有 WASAPI 侧车可扩展） |
| 当前播放媒体 | 从系统媒体会话取曲名 → 她评论这首歌 | 中（Windows SMTC） |

## 五、第三档：建立关系

这一档工程量大，但决定**长期黏性**——也就是"用了三个月还想用"。

### 5.1 长期记忆

**现状**：ACP 桥接是无状态的。她能聊，但不记得上次聊了什么。

**能做的**：

- 记住用户偏好（喜欢的音乐、常做的项目、作息习惯）
- 记住约定（"明天提醒我"）
- 记住共同经历（"上次那个 bug 修好了吗"）
- 对话中自然引用过往（这是"有记忆"和"没记忆"体感差距最大的地方）

**实现**：本地 JSON / SQLite 存记忆条目，对话时按相关性注入 ACP 上下文。你已经有一整套加密模型分发的经验，本地小数据库没有技术障碍。

**注意**：如果只是"把所有历史都塞进 prompt"，早晚会爆上下文。需要检索式记忆（关键词/向量召回），而不是全量投喂。

### 5.2 好感度与养成

**现状**：只有单次情绪，没有跨会话累积。

**能做的**：

- 交互行为累积好感度（点击、陪同时长、聊天轮次、按时休息）
- 好感度分档，每档解锁新台词 / 新表情 / 新服装
- **服装解锁直接接 3.1**——`外套`、`兔子`、`眼镜` 就是现成的奖励品，不需要美术
- 纪念日、连续陪伴天数

这是把 3.1 的换装从"功能"变成"玩法"的关键。单独的换装菜单只是个开关面板；接上养成它就是有意义的。

### 5.3 Agent 任务可视化（差异化最高）

**这是你最独特的优势，别人做不了。**

你已经通过 ACP 桥接了 WorkBuddy。那么 WorkBuddy 在做什么，她是知道的：

| Agent 状态 | 她的表现 |
|---|---|
| 空闲 | 正常待机 |
| 正在跑长任务 | 「工作中」姿态、打字/思考动作、齿轮转动 |
| 任务完成 | 抬头、报喜、可以播 `happy` 类表情 |
| 任务失败 | 沮丧、道歉 |
| 需要用户确认 | 举手、吸引注意 |
| 长任务卡住 / 耗时超预期 | 表现出焦急 |

**为什么这条最值钱**：一般的桌宠只能对你的鼠标键盘有反应，她还能对你**正在做的事**有反应。而且你实际的工作流里有大量长时任务（4 个 TetraMAX 压缩 STIL 文件串行转换、OOM 风险），这些恰好是最需要"有人看着"的场景。

**实现**：`workbuddy-bridge.js` 已经在收 ACP 事件，把事件类型映射到状态机即可。

### 5.4 语音输入（ASR）

**现状**：只有 TTS（她说），没有 ASR（你说）。

**价值**：不用打字就能跟她说话。对桌宠这种"随手交互"的场景，语音输入比输入框自然得多。

**实现选择**：

| 方案 | 优势 | 代价 |
|---|---|---|
| Web Speech API | 零依赖、Electron 内置 | 需联网、中文识别一般 |
| Whisper 本地（whisper.cpp） | 离线、准确度高 | 需引二进制/原生模块 |
| 复用已有 Python 环境 | 你有 `D:\index-tts` 和 `cosyvoice_src` 的 venv | 需扩展侧车进程 |

考虑到你已经有两个 Python venv（IndexTTS / CosyVoice），**扩展侧车是最顺的路径**——不用新引依赖体系。

## 六、手感类改造

这几点不影响功能面，但直接影响"好用感"。

### 6.1 抛掷物理

**现状**：拖拽是"跟手移动"，松手即静止。

**改造**：记录拖拽末段速度，松手后按惯性滑行、受"重力"下落、碰到屏幕边缘反弹、最终停稳。位置持久化（`window-bounds.json`）已经有，加一层速度状态机即可。

这是"可以玩"和"只能摆着"的分界线——可以把她甩到屏幕另一头。

### 6.2 边缘吸附

拖到屏幕左/右边缘时自动贴边，可以设置"半隐藏"（只露出半边）。配合 4.3 的全屏检测，全屏时自动缩到边缘。

### 6.3 环境风

`physics3.json` 有 67 个物理组、`头发物理1/2` 就有 69 个参数。加一个持续缓变的"风"输入（小幅摆动 `ParamAngleZ` 或专门的驱动参数），可以让头发和裙子始终有轻微飘动——不用做任何动作，画面就"活"了。

注意：这个效果**会与视线跟随抢参数**（`gaze.extra` 里已经在写 `ParamBodyAngleX/Y/Z`），要么走独立参数，要么并入同一个仲裁层（见第七节）。

## 七、前置工程：感知源仲裁

**这是所有感知类功能的地基，建议在第二档之前做。**

现状：`live2d-loader.js:310` 的 ticker 里有 6 个写者在抢同一批参数，靠两条隐性契约维持秩序：

- **调用顺序**：注释里明写「`_express` 必须在 `_blinkUpdate` 之后」「`_musicTick` 必须在 `_express` 之后」
- **手写时间窗互斥锁**：`_exprHoldUntil`、`_motionHoldUntil`

**问题**：这套机制是"约定"而非"机制"。加第 7、第 8 个写者（时间感知、在场感知、系统负载、Agent 状态）时会失控，而且失败方式很隐蔽——不是崩溃，是"某个表情偶尔不生效"。

**建议的最小改造**：

```
每个感知模块 → 只产出"意图"（想写哪些参数、优先级、持续时长）
            → 统一交给一个参数仲裁层
            → 仲裁层按优先级 + 混合权重写回模型
```

优先级可以简单定为：

```
瞬时表情（脸红/晕眩）  >  用户交互（点击/热键）  >  情绪
> Agent 状态  >  环境感知（风/呼吸/时钟）  >  待机动作
```

改造范围仅限 `live2d-loader.js` 的参数写入部分，不动 UI 与设置。做完之后，前面所有感知类功能都变成"注册一个意图源"，而不是"再记一条时序约束"。

## 八、两个待实测项

### 8.1 `ParamAngleX2` 可能才是主驱动

这次解析出的事实：

- `ParamAngleX/Y/Z`、`ParamBodyAngleX/Y/Z` 属于 **「驱动参数」** 组（6 个）
- `ParamAngleX2/Y2/Z2`、`ParamBodyAngleX2/Y2/Z2`、`ParamBodyAngleZ3`、`ParamBreath` 属于 **「主体」** 组（8 个）
- 两组的 `cdi3` 显示名**完全同名**（都是「角度 X」）

而物理的引用次数给出了强烈暗示：

| 参数 | 被多少个物理组引用 |
|---|---|
| `ParamBodyAngleX2` | **31** |
| `ParamBodyAngleZ2` | **25** |
| `ParamAngleX2` | **19** |
| `ParamAngleY2` | **19** |
| `ParamBodyAngleY2` | 9 |
| `ParamAngleX` | 3 |
| `ParamBodyAngleX` | 3 |
| `ParamAngleZ` / `ParamBodyAngleZ` | 2 / 2 |

**物理真正吃的是 `X2` 系列。** 而当前代码写的是 `ParamAngleX`（头部）和 `ParamBodyAngleX/Y/Z`（`gaze.extra`）——都不在主力位置上。

这意味着**视线跟随的效果可能一直是打了折的**：写进去的参数只牵动了少数几个物理组，头发、衣服、兽耳这些大件可能根本没跟着动。

**必须实测**：写 `ParamAngleX` 与写 `ParamAngleX2`，各截图对比，看头是否真的转、头发是否跟着飘。方法很简单——改值 → 截图 → 比对像素差。**建议优先做这个，因为它关乎一个已有功能是不是在空转。**

### 8.2 `HitAreas` 与 `LipSync` 组为空的连带影响

`model3.json` 里：

```json
{ "Target": "Parameter", "Name": "LipSync", "Ids": [] },
"HitAreas": []
```

- `LipSync` 组为空 → 口型只能靠 `vowelParamFamily: auto` 猜参数，不如显式指定稳定
- `HitAreas` 为空 → 分部位点击不可用（见 3.5）

两者都可以在 `injectModelAssets()`（`main.js:856`）里补上，不用改模型文件。

## 九、优先级建议

按「(回报 ÷ 成本)」排序，前五项建议依次做：

| 顺序 | 项目 | 成本 | 回报 | 说明 |
|---|---|---|---|---|
| 1 | **实测 `ParamAngleX2`** | 半小时 | 高 | 先确认已有功能是否在空转，避免在错的地基上加东西 |
| 2 | **换装系统**（3.1） | 半天 | 高 | 纯配置起步，立刻可见；后续可接养成 |
| 3 | **在场感知**（4.2） | 半天 | 极高 | `sleep` 动作是现成的，只差触发条件 |

| 6 | **前台应用感知**（4.3） | 2–3 天 | 高 | 解决"碍事"这个头号抱怨 |
| 7 | **感知源仲裁**（第七节） | 2–3 天 | 高（隐性） | 做完之后后面每一项都变简单 |
| 8 | **分部位点击**（3.5） | 1–2 天 | 中高 | 需要先测坐标 |
